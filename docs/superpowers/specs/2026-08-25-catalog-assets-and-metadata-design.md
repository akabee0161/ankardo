# カタログのアセット規約とメタデータ拡張 方針

作成日: 2026-08-25

本ドキュメントは作成時点の設計ログである。実装後に遡って更新しない。最新の状態を表す正典は `README.md` と `.claude/skills/new-game/SKILL.md` とする。

## 背景

カタログに登録されたゲームが3件になった。この段階で、サイトの完成度と運用規約を見直す。

現状の課題として、以下を確認した。

- `site/public/` が存在せず、スクリーンショットの置き場所が決まっていない。`Game` 型の `images` フィールドとその表示コンポーネント(`GameThumbnail` / `GameGallery`)は実装済みだが、3ゲームとも `images` 未設定で、全ゲームがプレースホルダー(ジャンル色＋タイトル頭文字)表示になっている
- 各ゲームが PC とスマートフォンのどちらに対応するか、スマートフォンの場合どちらの向きで遊ぶかがカタログのどこにも記載されていない
- 操作方法がカタログに記載されていない
- `app/layout.tsx` に共通ヘッダー/フッターがなく、`/games` や `/games/<slug>` からトップへ戻る導線がない
- `site/` にテストが1本もなく、`package.json` に `test` script も存在しない

## サイトの位置づけ

最終的には一般公開して外部からの流入を得ることを目標とするが、当面は身内・知人の範囲で利用し、使用感を高める段階とする。

この前提から、当面の対応方針を次のように定める。

- 対応する: 見た目の完成度、遊びやすさ、サイト内の回遊導線
- 当面対応しない: SEO 対策、OGP 画像、アナリティクス、収益化
- 将来の移行時に作り直しが発生しないよう、URL 構造とメタデータの器は正しい形で用意しておく

## 全体の段階分け

対応項目を3段階に分ける。本ドキュメントは段階①のみを対象とする。

| 段階 | 内容 |
|---|---|
| ① | スクリーンショットの規約策定と投入、データモデル拡張(対応デバイス・操作方法)、バリデーション・テスト・ドキュメント整備 |
| ② | 共通ヘッダー/フッター、ファビコン、ワードマーク |
| ③ | ジャンル絞り込み |

段階を分ける理由は、①でスクリーンショットが入った実際の画面を確認してから②のデザインを決める方が、判断の根拠が得られるためである。

段階③を最後にするのは、`GENRES` に定義された7ジャンルのうち実際に使われているのが3ジャンル(`action` / `puzzle` / `simulation`)であり、現状で絞り込み UI を作ると空のジャンルが並ぶためである。ただし段階③の実装時には、定義済みの全ジャンルではなく「実際にゲームが存在するジャンル」だけを表示する方式にすることで、この問題は回避できる。

以下の項目は検討したうえで対応しないことにした。

- 一覧の並び替え機能: ゲーム3件では選択肢として機能しない
- スクリーンショットの自動生成(CI での Playwright 撮影): 現在の更新頻度ではスクリーンショットの撮り直しがほとんど発生せず、削減できる手間がない。また自動撮影で得られるのは主にタイトル画面であり、カード表示に適した画面を撮るにはゲーム側への撮影用フックの実装が別途必要になる。後から導入する場合の障壁は CI の有無ではなく規約の不在であるため、本ドキュメントで規約を確定させることで、将来同じパスへ画像を出力する形で追加できる

## 1. スクリーンショットの規約

### 置き場所とファイル名

`site/public/screenshots/<slug>/01.png` に置き、`/screenshots/<slug>/01.png` として参照する。

`public/games/<slug>/` としない理由は、ページのルートが `/games/<slug>/` であり、`trailingSlash: true` の静的書き出しでは `out/games/<slug>/index.html` が生成されるためである。同じディレクトリに HTML と画像が混在すると、パスがページを指すのかアセットを指すのか判別しづらくなる。

ファイル名は `01.png`, `02.png` の連番とする。`GameThumbnail` が `images[0]` を参照するため、先頭のファイルが一覧カードのサムネイルになる。

### 枚数

1〜5点。`images` は現行どおり任意フィールドのままとする。新しいゲームを登録した直後で画像が未用意の場合に、既存のプレースホルダー表示へフォールバックさせるためである。

### 比率

16:9 で撮影し、表示側も 16:9 に統一する。

現在の表示側は場所ごとに比率が異なり、いずれも `object-cover`(中央基準の切り取り)を使っている。

| 場所 | 現在の指定 | 実効比率 | 16:9 画像を入れた場合の切り取り |
|---|---|---|---|
| 一覧カード | `h-40` 固定・幅可変 | 約 2:1 | 上下が約11%欠ける |
| 詳細メイン画像 | `h-48` / `sm:h-72` 固定・幅可変 | 約 2.56:1 | 上下が約30%欠ける |
| ギャラリーのサムネイル | `64x64` | 1:1 | 左右が約44%欠ける |

詳細ページのメイン画像で上下が3割欠けると、画面上下端に配置されることの多いスコア表示や操作ボタンが失われる。

対応として、一覧カードと詳細メイン画像を固定高さから `aspect-video` に変更し、切り取りを発生させない。ギャラリーのサムネイルは一覧性を優先して `64x64` のままとする。選択用の小さな表示であり、切り取られても実害がないためである。

この変更により、詳細ページのメイン画像は PC で最大 736×414px になる(`max-w-3xl` の768pxから左右パディング32pxを引いた幅。現行の `h-72` は高さ288px)。画像の存在感は増すが、閲覧者にとって「どのような画面のゲームか」が主要な判断材料であることから、この方向を採用する。

### 解像度とファイルサイズ

1280×720 を基本とし、1枚あたり 300KB 以内を目安とする。

`next.config.js` で `images: { unoptimized: true }` が指定されており、静的書き出しのため Next.js の画像最適化は動作しない。撮影したファイルがそのまま配信されるため、サイズは撮影時に管理する必要がある。PNG で 1280×720 の場合にサイズ目安を超えるときは WebP を使う。

変換スクリプトは用意しない。対象が3ゲーム分であり、手作業の方が早いためである。

### 撮影時の注意

`rungame-sample` は Phaser の論理解像度が 720×405、`character-tactics` は Canvas の論理解像度が 960×540 で、いずれも 16:9 である。ブラウザのウィンドウ比率が 16:9 でない状態で撮影すると、ゲーム描画領域の周囲に余白が入る。描画領域だけを切り出すか、ウィンドウを 16:9 に合わせて撮影する。

`shogi-vs-cpu` は DOM ベースで固定解像度を持たないため、16:9 に収まるようウィンドウを調整して撮影する。

## 2. データモデルの拡張

`Game` 型(`site/lib/games.ts`)に2つのフィールドを追加する。

### `devices`(必須)

```ts
type DeviceKey = "pc" | "mobile-landscape" | "mobile-portrait";
devices: DeviceKey[];
```

| 値 | 表示ラベル |
|---|---|
| `pc` | 💻 PC |
| `mobile-landscape` | 📱 スマホ・タブレット(横向き) |
| `mobile-portrait` | 📱 スマホ・タブレット(縦向き) |

デバイスと画面の向きを別フィールドに分けず、値として合成する。分離した場合、PC のみ対応のゲームに向きを指定するような意味を持たない組み合わせが表現可能になり、それを排除するバリデーションが別途必要になるためである。

タブレットをスマートフォンと区別しない。操作系(タッチ)と持ち方の指示が同一で、区別しても情報が増えないためである。

`genre` と同様に列挙型とし、ビルド時に検証する。自由文字列にしない理由は、段階③のジャンル絞り込みで「スマートフォンで遊べるものだけ」といった条件に使える形にしておくためである。既存の `ageRange` / `players` / `difficulty` は自由文字列だが、これらは表示専用であり表記ゆれが実害にならない。

必須フィールドとする。既存3件の JSON への追記が必要になるが、デバイス情報を持たないゲームが混在すると段階③での扱いが煩雑になる。

### `controls`(任意)

```ts
controls?: string[];
```

操作方法を箇条書きの配列で持つ。デバイスごとの構造化(`{ pc: ..., mobile: ... }`)は行わない。記載したい内容がゲームごとに異なり、構造を先に固定すると当てはまらない項目が発生するためである。

任意フィールドとするのは、操作が自明なゲームで記載を強制しないためである。

### 既存3ゲームの値

各リポジトリの `origin/main` のコードを確認して判定した。

| ゲーム | 根拠 | `devices` |
|---|---|---|
| `rungame-sample` | `src/utils/orientationLock.ts` が `screen.orientation.lock('landscape')` を実行する。入力は `keydown-SPACE` / `keydown-UP` / `pointerdown` の3系統 | `["pc", "mobile-landscape"]` |
| `character-tactics` | Canvas の論理解像度が 960×540 固定で、`src/render/viewport.ts` の `computeViewport()` が縮小して中央寄せする。`index.html` は `user-scalable=no` / `touch-action: none` / `overflow: hidden` を指定 | `["pc", "mobile-landscape"]` |
| `shogi-vs-cpu` | `src/ui/style.css` は縦積みが既定で、`@media (min-width: 768px) and (orientation: landscape)` のときのみ横並びに切り替わる。ボタンは `min-width` / `min-height` 44px を確保 | `["pc", "mobile-portrait"]` |

`shogi-vs-cpu` の判定はコードからの推論であり、実機で確認していない。横向き指定が 768px 以上のときにのみ適用されることから、スマートフォンでは横向きにしても縦レイアウトのままになると読める。実機確認で異なる結果が出た場合は値を修正する。

`controls` の内容は、撮影・実機確認とあわせて確定する。`rungame-sample` については `src/utils/jumpController.ts` の `maxJumps = 2` からダブルジャンプが可能と読める。

### 表示場所

- `devices`: 既存の `MetaBadges` に並べる。`MetaBadges` は `flex-wrap` を指定済みのため、バッジが4種類になっても折り返す
- `controls`: 詳細ページの説明文の下に「あそびかた」として表示する。一覧カードには表示しない

## 3. バリデーション、テスト、ドキュメント

### `lib/devices.ts` の新規作成

`lib/genres.ts` と同じ構成で、値と表示ラベルを1箇所に定義する。

```ts
export type DeviceKey = "pc" | "mobile-landscape" | "mobile-portrait";

export const DEVICES: Record<DeviceKey, { label: string; icon: string }> = {
  "pc": { label: "PC", icon: "💻" },
  "mobile-landscape": { label: "スマホ・タブレット(横向き)", icon: "📱" },
  "mobile-portrait": { label: "スマホ・タブレット(縦向き)", icon: "📱" },
};
```

`genres.ts` と異なり配色のクラス名は持たない。`MetaBadges` の既存バッジ(白背景・グレー枠)の見た目に揃えるため、色の定義が不要である。色を持つのはジャンルのみという現在の区別も維持される。

### バリデーションの拡張

`site/lib/games.ts` の `validateGame` に以下を追加する。

- `devices`: 配列であること、要素が1つ以上あること、各要素が `DEVICES` のキーであること、重複がないこと
- `controls`: 未設定を許容し、設定されている場合は各要素が空でない文字列の配列であること(`images` と同じ検証形)

空配列を許容しない。`[]` は「どのデバイスでも遊べない」という意味になり、必須にした意図が失われる。重複(`["pc", "pc"]`)も許容しない。同一のバッジが2つ表示される状態になるため、記述時に検出できる方がよい。

### テストの導入

Vitest を導入する。3つのゲームリポジトリがいずれも Vitest を使用しており、リポジトリ間で作法を揃えられる。

テスト対象は `validateGame` に限定する。この関数は現在 `export` されていないため、テストのために `export` する。`getAllGames()` 経由でテストすると `fs` とフィクスチャのディレクトリが必要になり、検証ロジックを確認する目的に対して準備が重くなる。

| # | ケース | 期待 |
|---|---|---|
| 1 | 全フィールドが正しい | 通る |
| 2 | 必須文字列フィールドが欠落、または空文字 | エラー |
| 3 | `genre` が `GENRES` に存在しない値 | エラー(既存挙動の回帰) |
| 4 | `devices` が欠落、空配列、不正な値、重複 | エラー |
| 5 | `controls` が配列でない、または空文字を含む | エラー |
| 6 | `images` が配列でない、または空文字を含む | エラー(既存挙動の回帰) |
| 7 | `controls` / `images` が未設定 | 通る |

表示コンポーネント(`GameCard` / `GameThumbnail` / `GameGallery` / `MetaBadges`)のテストは追加しない。ロジックを持たず、JSX がそのまま出力されることを確認するだけになるためである。

### CI への追加

`.github/workflows/site.yml` の `npm run build` の前に `npm test` を追加する。`.claude/skills/new-game/SKILL.md` の手順4がゲームリポジトリに対して「テストがあれば build 前に実行する」ことを要求しており、カタログ側も同じ扱いにする。

### ドキュメントの更新

- `.claude/skills/new-game/SKILL.md` 手順5: JSON テンプレートに `devices`(必須)と `controls`(任意)を追加する。スクリーンショットの規約(置き場所、命名、比率、枚数、サイズ目安)もここに記載する。新しいゲームを追加する際に最初に参照する場所であるため
- `README.md`: 必須フィールドの一覧に `devices` を追加する

`docs/superpowers/` 配下の既存 spec は更新しない。作成時点のログとして扱う運用ルールがあるためである。

## 実装に含まれない作業

スクリーンショットの撮影と配置は手作業として残る。規約、置き場所、`images` フィールドの枠までは実装で用意するが、実際の画像ファイルはユーザーが撮影して配置する必要がある。

`shogi-vs-cpu` の `devices` 判定、および3ゲームの `controls` の内容は、実機確認を経て確定する。

## 未決事項

- 段階②(共通ヘッダー/フッター、ファビコン、ワードマーク)の設計は、段階①完了後にスクリーンショットが入った画面を確認してから決める
- 段階③(ジャンル絞り込み)で、絞り込みの軸をジャンルのみとするか `devices` や `ageRange` も含めるかは、段階③の設計時に判断する
